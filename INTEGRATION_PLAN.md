# План объединения DataBaseGenerator и DicomGenerator

Цель: одно настольное приложение Medical TestKit для подготовки тестовых данных. Оно генерирует записи в MySQL и LiteDB, создаёт DICOM-файлы, отправляет их на PACS, сканирует каталоги и PACS и сохраняет извлечённые метаданные обратно в базу.

Старые приложения не удаляются, пока новый набор экранов не повторяет их сценарии.

## Зачем объединять

Сейчас это два отдельных WPF-приложения на .NET 9, CommunityToolkit.Mvvm и MahApps.Metro. Оба используют LiteDB 5.0.21. Модели пациента, исследования, серии и изображения почти совпадают, но уже начали расходиться.

Полезный тестовый цикл один:

1. Создать пациента и исследование в базе.
2. Собрать DICOM с теми же Patient ID, Study UID и Accession Number.
3. Отправить файлы на PACS.
4. Просканировать каталог или PACS.
5. Сохранить результат в LiteDB.
6. Сравнить ожидаемое и фактическое.

Пока генераторы пациентов независимы, такой сценарий приходится собирать руками.

## Чего не делать

- Не переносить экраны и ViewModel из DicomGenerator в DataBaseGenerator как есть.
- Не сливать два Git-репозитория в один коммит.
- Не менять одновременно WebHost, схему MySQL и DICOM-генерацию.
- Не делать общую базу «на все случаи», пока не зафиксирован общий набор моделей.
- Не выключать старое приложение DicomGenerator до функционального паритета.

Генерация DICOM, отправка, сканирование и запись в LiteDB сейчас живут внутри ViewModel и WPF-проекта DicomGenerator. Если перенести их вместе с окнами, получится один большой монолит.

## Целевое устройство

Оболочкой остаётся текущий WPF-проект DataBaseGenerator. Новые возможности добавляются страницами в существующее меню.

```text
DataBaseGenerator.UI.Wpf          оболочка, страницы, диалоги
DataBaseGenerator.Web             MySQL API, пока без изменений
DataBaseGenerator.Core
  MySqlGenerator                  как сейчас
  LiteDbGenerator                 как сейчас
  Dicom                           генерация, разбор, PACS, отправка
  Scenarios                       сценарии, которые связывают шаги
```

Общий объект сценария создаётся один раз и превращается в запись MySQL, документ LiteDB, набор DICOM-тегов и при необходимости в WorkList.

Имя продукта в заголовке окна можно сменить позже. На время перехода пункты меню остаются узнаваемыми: MySQL, LiteDB, DICOM, PACS, Сканер, Сценарии.

## Расхождения, которые закрываются до переноса

| Тема | Сейчас | Что сделать |
|---|---|---|
| Платформа Core | DataBaseGenerator.Core — net8.0, DicomGenerator.Core — net9.0 | Поднять Core генератора баз до net9.0 отдельным шагом и прогнать тесты |
| Модели LiteDB | Почти копии. В DICOM есть Occupation, в базе исследований есть SnapshotPatientSex | Выбрать одну схему и явно описать миграцию существующих файлов .db |
| Идентификаторы | MySQL PatientID вида MXE + номер; DICOM ID собирается из префикса и числа | В сценарии задавать Patient ID один раз и передавать его в оба генератора |
| Конфигурация | В DICOM зашиты пути `D:\Develop\DicomGeneratorTestData` и `E:\DicomGeneratorResult`, PACS 127.0.0.1:4242 | Вынести в именованные профили: папки, AE Title, порт, файл LiteDB, строка MySQL |
| Фоновые операции | У каждого ViewModel свой прогресс, отмена и текст статуса | Общий механизм задания: процент, сообщение, отмена, длительность, итог |
| WebHost | WPF сам запускает опубликованный DataBaseGenerator.Web.exe | На первых шагах не трогать |

## Шаг 0. Зафиксировать текущее поведение

Срок: 1–2 дня. Оба приложения остаются рабочими.

Записать короткие контрольные сценарии и ожидаемый результат:

- MySQL: создать N пациентов, обновить список, отфильтровать, добавить один вручную, удалить.
- LiteDB: открыть файл только для чтения, переключить запись, добавить пациента, сгенерировать исследования.
- DICOM: сгенерировать маленькую пачку DX/MG/SR в пустую папку.
- PACS: C-ECHO и отправка нескольких файлов на тестовый Orthanc.
- Сканер: папка с этими файлами и сохранение в отдельный .db.

Эти сценарии — критерий, что перенос ничего не сломал. Автотесты на DICOM-сеть не обязательны: достаточно ручного чек-листа.

## Шаг 1. Поднять Core генератора баз до .NET 9

Отдельный коммит, без DICOM-кода.

- Сменить `TargetFramework` у `DataBaseGenerator.Core` с net8.0 на net9.0.
- Проверить сборку UI, Web и тестового проекта.
- Не обновлять заодно EF Core, Pomelo и LiteDB.

Готово, когда решение собирается и контрольные сценарии MySQL и LiteDB проходят.

## Шаг 2. Вынести DICOM-логику из окон

В репозитории DicomGenerator, не вливая его в генератор баз.

Новые типы без `System.Windows`, `MessageBox` и диалогов выбора папки:

- `DicomGenerationService` — то, что сейчас делает цикл в `FileGeneratorViewModel.GenerateFiles`.
- `DicomStoreService` — отправка пачки из `FileSenderViewModel`.
- `DicomFolderScanner` и `DicomPacsScanner` — обход каталога и C-FIND/C-GET.
- `DicomMetadataStore` — запись пациента, исследования, серии и изображения в LiteDB. Сейчас это `DicomDatabaseService` внутри WPF-проекта.

ViewModel после этого только собирает параметры, вызывает сервис и показывает прогресс.

Перенос файлов:

- `DicomFileScanner` и `DicomParser` лежат в UI-проекте, но объявлены в пространстве имён `DicomGenerator.Core.DicomFileParser`. Их место — Core.
- `LocalPacsSource` и `LiteDbContext` уезжают из UI в Core вместе со сканером.
- `fo-dicom` остаётся зависимостью DICOM-проекта, не всего UI.

Готово, когда три вкладки DicomGenerator работают через сервисы, а поведение чек-листа из шага 0 не изменилось.

## Шаг 3. Общая модель тестовых данных

Один набор моделей на оба инструмента. Практичный вариант — оставить модели LiteDB генератора баз и добавить в них недостающие поля из DICOM-моделей (`Occupation` и всё, что реально пишется парсером).

Правила:

- Patient ID — строка, одна и та же в MySQL, LiteDB и теге DICOM Patient ID.
- Study Instance UID и Series/SOP Instance UID создаёт DICOM-генератор. База их хранит, но не выдумывает заново при импорте.
- Пол хранится как M/F/O. Отображение «Man / Female / Other» остаётся в UI.
- Существующие .db не мигрируются молча. Если схема не совпала, приложение сообщает, что файл от старой версии, и предлагает открыть его только для чтения или сохранить копию.

На этом шаге генераторы ещё не вызывают друг друга. Они только принимают уже созданный Patient ID и демографию.

## Шаг 4. Профили окружения

Один JSON-профиль, например `profiles/local-orthanc.json`:

- строка MySQL;
- путь к LiteDB пациентов и к LiteDB planned studies;
- папка тестовых DICOM-шаблонов;
- папка результата генерации;
- список PACS: host, port, calling AE, called AE;
- папки для сканирования.

В интерфейсе профиль выбирается, а не зашивается в конструктор ViewModel. Секреты MySQL не коммитятся: в репозитории лежит пример без пароля.

## Шаг 5. Встроить страницы в оболочку DataBaseGenerator

Меню DataBases получает раздел DICOM с тремя страницами, повторяющими текущие вкладки:

- Generate;
- PACS;
- Парсинг DICOM.

Страницы новые, но тонкие: они вызывают сервисы из шага 2. Старые UserControl из DicomGenerator не копируются.

Оболочка уже умеет показывать одну страницу в `CurrentPage`. Новые страницы подключаются так же, как MySQL и LiteDB.

WebHost по-прежнему стартует только для MySQL. DICOM-страницы его не требуют.

Готово, когда из одного окна выполняются контрольные сценарии обоих приложений.

## Шаг 6. Связанный сценарий

Отдельная страница «Сценарий», первый пресет «База и DICOM»:

1. Создать пациента в LiteDB или MySQL.
2. Сгенерировать DICOM с его Patient ID, ФИО, полом и датой рождения.
3. По желанию отправить папку на PACS из профиля.
4. Показать итог: сколько пациентов, исследований, серий и файлов, куда записано, была ли отмена или ошибка.

Второй пресет, после того как первый стабилен: «Проверка PACS». Сканер читает тот же PACS или папку и показывает, какие Patient ID и Study UID из шага генерации найдены, а какие нет.

Сценарий не заменяет ручные страницы. Ручные страницы нужны, когда проверяется один шаг.

## Шаг 7. Вывести DicomGenerator из работы

Только после паритета по чек-листу шага 0 и после двух пресетов шага 6.

- В README DicomGenerator указать, что инструмент переехал, и дать путь к новому меню.
- Репозиторий оставить читаемым, новые функции туда не добавлять.
- Общие сервисы живут в Core генератора баз. Копировать их обратно не нужно.

Удалять репозиторий DicomGenerator не требуется.

## Порядок коммитов

Каждый шаг — отдельный обозримый коммит в DataBaseGenerator, кроме шага 2: он коммитится в DicomGenerator, пока код ещё там.

1. Чек-лист текущего поведения.
2. Core на net9.0.
3. Сервисы DICOM без UI.
4. Общие модели и правило для старых .db.
5. Профили окружения.
6. Три страницы DICOM в оболочке.
7. Страница сценария.
8. Пометка старого приложения как перенесённого.

## Риски

- Схема LiteDB разъедется, если править модели в двух репозиториях одновременно. После шага 3 правится только одна копия.
- Большая генерация DICOM и сканирование PACS блокируют UI, если оставить их в обработчике кнопки. Сервисы принимают `CancellationToken` и `IProgress`.
- Отправка на PACS пачками по 500 ассоциаций уже есть. При переносе размер пачки и AE Title берутся из профиля, а не из полей по умолчанию в коде.
- WebHost, запущенный из WPF, легко забыть при проверке MySQL. DICOM-изменения его не касаются, но сценарий «MySQL + DICOM» нужно проверять с поднятым хостом.

## Что считать окончанием перехода

Одно окно. MySQL, LiteDB, генерация DICOM, отправка на PACS и сканер открываются из его меню. Хотя бы один сценарий проходит от создания пациента до найденного на PACS исследования без ручного копирования Patient ID. Старое приложение DicomGenerator больше не нужно для ежедневной работы.
